# Channel Stat Bot

Telegram-бот на Node.js и Telegraf для учёта вступлений и выходов из одного канала. Сохраняет периоды подписки, источник вступления и превью поста, полученного отдельным запросом к Telegram на момент события; отправляет владельцу уведомления.

## Запуск

1. Установите зависимости: `npm install`.
2. Скопируйте `.env.example` в `.env` и заполните настройки:
   - `BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather).
   - `OWNER_ID` — положительный числовой ID вашего Telegram-аккаунта.
   - `CHANNEL_ID` — отрицательный числовой ID канала, обычно начинающийся с `-100`. Имя вида `@channel` не подходит для сравнения с входящими событиями.
3. Добавьте бота администратором канала, чтобы Telegram присылал события об изменении участников.
4. Чтобы создавать размеченные ссылки, выдайте боту право приглашать пользователей (`can_invite_users`).
5. Откройте личный чат с ботом и отправьте `/start`, чтобы он мог присылать вам уведомления. Команда `/link campaign_name` создаёт ссылку для рекламного источника; метка должна содержать от 1 до 32 символов.
6. Для разработки запустите `npm run dev` (nodemon следит только за JavaScript в `src/`, поэтому запись статистики не перезапускает бота).
7. Для обычного запуска используйте `npm start`.

Отслеживаемый канал должен быть указан как личный канал в профиле владельца (`OWNER_ID`). Бот проверяет, что его ID совпадает с `CHANNEL_ID`, и получает существующие посты через [getUserPersonalChatMessages](https://core.telegram.org/bots/api#getuserpersonalchatmessages). Для этого не нужно публиковать тестовый пост или входить в Telegram от имени пользователя.

Файл `.env` исключён из Git. Команды и текстовые сообщения доступны только владельцу. На обычный текст и `/start` бот отвечает `✅ Бот работает`.

Команда `/stats` показывает сводку за предыдущие завершённые сутки статистики Telegram: с 00:00 до 23:59:59 UTC. Отправка ежедневной сводки привязана отдельно к 06:00 по Подгорице. Команда использует тот же формат и доступна при подключённом аккаунте Telegram (`SOURCE_STATS_ENABLED=1`), даже если автоматическая отправка отключена. Отчётная дата меняется в полночь UTC.

## Проверка

Запустите `npm test`. Тесты работают с временными файлами и подменёнными вызовами Telegram, без токена и подключения к сети.

Для живой проверки добавьте `DEBUG_MEMBER_UPDATES=1` в `.env` и перезапустите бота. В `data/debug-member-updates.jsonl` появятся исходные события `chat_member` настроенного канала и результат их обработки. После проверки выключите флаг: журнал содержит данные участников и растёт при новых событиях.

На Railway этот флаг нужно задавать в Variables сервиса: локальный `.env` не переносится на сервер. При `DEBUG_MEMBER_UPDATES=0` или отсутствующем значении обработчик журнала не подключается и файл не создаётся. При включённом журнале запись `observer_started` создаётся сразу при запуске, ещё до первого вступления. Для сохранения статистики и журнала между деплоями подключите постоянный volume к `/app/data`.

## Структура

- `src/index.js` — загрузка `.env`, запуск и остановка бота.
- `src/config.js` — чтение и проверка настроек.
- `src/bot.js` — сборка бота и регистрация обработчиков без запуска polling.
- `src/controllers/` — команды, события участников и посты канала.
- `src/middleware/owner-only.middleware.js` — доступ владельца к командам и сообщениям.
- `src/middleware/ordered-channel-updates.middleware.js` — обработка событий канала в порядке получения, включая события из одной пачки Telegram.
- `src/services/member-event.service.js` — преобразование событий Telegram и создание превью постов.
- `src/services/channel-post.service.js` — запрос последних постов и выбор публикации на момент вступления или выхода.
- `src/storage/member.store.js` — хранение статистики в JSON и последовательная очередь записи.
- `src/services/daily-summary-monitor.service.js` — ежедневная сводка и повтор отправки после ошибок.
- `src/services/telegram-post-statistics.service.js` — чтение счётчиков пяти последних публикаций.
- `src/services/telegram-post-daily-statistics.service.js` — расчёт активности постов за календарный день по историческим графикам Telegram.
- `src/storage/daily-summary.store.js` — снимки счётчиков и состояние отправки сводок.
- `tests/` — проверки обработчиков, хранения и их совместной работы.

## Данные

Файл `data/channel-members.json` создаётся автоматически и не попадает в Git. Формат: `{ latestPost, members }`. Каждая запись `members` описывает один период подписки; выход без известного вступления сохраняется с `addedAt: null`. Повторное вступление после выхода помечается `returned: true`.

Вступление при уже открытом периоде подписки и повторный выход с тем же временем не создают новых записей или уведомлений. События старше последнего сохранённого изменения участника игнорируются. Уже накопленные записи автоматически не очищаются.

Запись выполняется через временный файл с последующим переименованием. Повреждённый JSON или неподходящая структура вызывают ошибку, исходный файл сохраняется. Запускайте один экземпляр бота на файл данных: очередь защищает записи внутри одного процесса.

При каждом вступлении и выходе бот отдельно запрашивает до 20 последних постов и выбирает последнюю публикацию, опубликованную не позже события. В `postAtAddition` или `postAtRemoval` попадают первые 100 Unicode-символов её текста или подписи. Для этого не требуется ранее получать событие `channel_post`. Поле `postedAt` в снимке хранит время публикации или последней учтённой правки. Для постов без текста превью равно `null`.

Если запрос не удался, канал не привязан к профилю, событие старше доступных 20 публикаций или нужный пост отредактирован уже после события, членство всё равно сохраняется. Причина отсутствия снимка записывается в `postAtAdditionError` или `postAtRemovalError` и в лог. Пустой канал даёт `null` без ошибки. Удалённые посты и прежние версии отредактированного текста этот запрос восстановить не может.

`latestPost` остаётся локальным снимком для просмотра, но не используется вместо запроса при записи членства. Новые посты и правки также обновляют этот снимок; существующие снимки в записях участников остаются прежними.

### Уведомление о вступлении

Бот сообщает о вступлении сразу после записи события:

```text
🎉 На канале новый пользователь – Анна Иванова (@anna)
```

Как только источник определён, приходит отдельное сообщение:

```text
Обновилась информация о том, откуда пришел пользователь Анна Иванова (@anna): Ads (Название кампании)
```

Если кампания ещё проверяется, в сообщении будет только `Ads`; после её определения придёт уточнение. Для URL показывается название действующего URL-промо. Если username отсутствует, скобок после имени нет. Возможные источники: `Ads`, `URL`, `Shareable Chat Folders`, `Search`, `PM`, `Пригласительная ссылка`, `Заявка на вступление`.

Бот проверяет статистику примерно каждые 30 секунд. Если источник неизвестен через 30 минут после вступления, он пришлёт сообщение с предложением ответить `URL`, `Ads`, `Search`, `PM` или `Chat Folder`. Проверки продолжатся и после этого срока: позднее определение источника также вызовет уточнение. Ответить можно на сообщение о вступлении или о неизвестном источнике. При отключённой статистике доступные сведения события Telegram отправляются сразу. Ошибки получения поста остаются в данных и логе.

Состояние первого сообщения хранится в `joinNotification`, а уточнения — в `sourceNotification`. Отправленные сообщения сохраняют статус, время и ID для ответа владельца. Неотправленные сообщения повторяются после следующей проверки или перезапуска. Старые записи без `joinNotification` автоматически в очередь не добавляются.

### Уведомление о возвращении

Для повторного вступления (`returned: true`) используется отдельный заголовок и добавляется вся сохранённая история этого пользователя:

```text
🎉 На канале пользователь-возвращенец – Анна Иванова (@anna)

Информация о прошлых добавлениях:

Добавился: 01.09.2026 10:00
Источник: URL
Пришел из-за поста: Пост при вступлении https://t.me/c/1234567890/10
Удалился: 03.09.2026 12:00
Удалился из-за поста: Пост при отписке https://t.me/c/1234567890/12
Сколько дней провел на канале: 2
```

Блок из шести строк повторяется для каждого предыдущего периода по порядку от старого к новому. История выбирается по ID пользователя; текущий вход и любые более поздние записи в неё не попадают, даже если статистика для уведомления пришла с задержкой. Источник текущего входа приходит отдельным уточнением; в каждом блоке истории используется источник того периода и доступное название кампании.

Даты выводятся в формате `ДД.ММ.ГГГГ ЧЧ:ММ`, часовой пояс — `Europe/Podgorica` с учётом летнего времени. Длительность рассчитывается отдельно для каждого периода так же, как в уведомлении об отписке. Для обоих постов выводятся первые 100 Unicode-символов превью и ссылка по сохранённому ID. Неизвестные даты и отсутствующие посты обозначаются `нет данных`; запись с известным выходом и неизвестным вступлением также включается.

Если история превышает [лимит сообщения Telegram](https://core.telegram.org/bots/api#sendmessage), она отправляется несколькими сообщениями без сокращения списка периодов. По возможности границы частей проходят между целыми периодами. Все части готовятся после проверки текущего источника и кампании; предпросмотр ссылок отключён.

### Уведомление об отписке

```text
👎 Подписчик покинул канал! Да и хуй с ним.

Имя: Анна Иванова (@anna)
Источник: Ads (Название кампании)
С какого поста подписался: Первые 100 символов поста https://t.me/example_channel/128
Сколько дней провел на канале: 3
```

Имя и username берутся из события отписки; без username скобок после имени нет. Данные для остальных строк берутся из записи участника, закрытой именно этим событием. Если у неё нет `addedAt`, сообщение заканчивается после имени, даже когда в JSON есть более ранние периоды подписки этого пользователя. Источник использует те же названия, что и сообщение о вступлении; кампания в скобках появляется только для `Ads`.

Пост берётся из `postAtAddition` этой записи: показываются первые 100 Unicode-символов `preview` и ссылка по `messageId`. Для поста без текста выводится `Пост без текста`, при отсутствии снимка — `нет данных`. Используется [формат ссылок Telegram на сообщения](https://core.telegram.org/api/links#message-links): публичная ссылка с username канала или ссылка `t.me/c/…` по ID канала, если username отсутствует. Предпросмотр ссылки отключён.

Длительность — число полных суток по 24 часа между `addedAt` и `removedAt`. Если прошло меньше суток, выводится `меньше 1`. При повторной подписке учитывается только закрываемый период, предыдущие периоды не суммируются. Ошибки получения постов остаются в JSON и логе, без технических строк в уведомлении.

### Способ вступления и статистика источников

В [ChatMemberUpdated](https://core.telegram.org/bots/api#chatmemberupdated) доступны `invite_link`, `via_chat_folder_invite_link` и `via_join_request`. Обработчик сохраняет их как `invite_link`, `chat_folder` и `join_request` соответственно. Если этих признаков нет, сохраняется `unknown`: это не означает органический переход или отсутствие рекламы.

Категории из статистики канала нельзя целиком восстановить для каждого подписчика по событиям Bot API:

| Категория статистики | Что доступно при вступлении |
| --- | --- |
| URL | `invite_link` позволяет определить вступление по пригласительной ссылке, когда Telegram передал её. Это не универсальный признак перехода по любому URL и не гарантированное соответствие категории статистики. |
| Ads | Отдельного признака в `ChatMemberUpdated` нет. |
| Shareable Chat Folders | `via_chat_folder_invite_link: true`. |
| Search | Отдельного признака в `ChatMemberUpdated` нет. |
| PM | Отдельного признака в `ChatMemberUpdated` нет. Поле `from` обозначает исполнителя изменения, а не чат, из которого пришёл пользователь. |

Общие числа по источникам доступны в `stats.broadcastStats.new_followers_by_source_graph` через [stats.getBroadcastStats](https://core.telegram.org/method/stats.getBroadcastStats). Этот метод Telegram API доступен пользовательским аккаунтам, а не ботам. Он возвращает график статистики, а не соответствие источников конкретным подписчикам.

Дополнительные запросы пользовательского Telegram API могут восстановить часть сведений о вступлениях. [messages.getChatInviteImporters](https://core.telegram.org/method/messages.getChatInviteImporters) возвращает участников конкретной пригласительной ссылки с `user_id` и временем вступления; [channels.getAdminLog](https://core.telegram.org/method/channels.getAdminLog) позволяет проверить доступные события, включая вступление по приглашению. Эти методы требуют пользовательского аккаунта с правами администратора и недоступны с токеном бота. Они не дают универсальную привязку Ads / Search / PM к пользователю и не распространяются на любую публичную ссылку вида `t.me/channel`.

При `SOURCE_STATS_ENABLED=1` бот после каждого нового вступления запрашивает этот график и сравнивает накопительные счётчики за день UTC с предыдущим снимком. Например, `Ads=1, URL=0` → `Ads=1, URL=1` означает URL для следующего участника; последующий рост до `Ads=2, URL=1` означает Ads. Для первого дня работы бот сначала получает исходный снимок; в новом дне сравнение начинается с нулей. Выходы и повторно доставленные события не запускают запрос.

Счётчики хранятся отдельно в `data/source-statistics.json`: `days` содержит предыдущие использованные `counts`, последние полученные `observedCounts` и время проверки; `pending` — ожидающие вступления, `decisions` — результаты сравнения с разницей счётчиков. В `channel-members.json` остаются участники, их `source` и статус проверки `sourceLookup`, без дневных счётчиков. Решение сначала сохраняется в файле статистики, затем применяется к участнику; после прерывания между записями оно применяется повторно без повторного расходования прироста.

Если вырос ровно один источник на число ожидающих вступлений, участники получают этот источник с `attribution: "statistics_delta"`. Подтверждённые владельцем источники и сведения Bot API сохраняют приоритет. Если Telegram ещё не обновил график, исходные счётчики не расходуются: бот повторяет проверку через 30 секунд, а найденный источник отправляет отдельным сообщением. Ограничение Telegram `FLOOD_WAIT` увеличивает паузу. При неоднозначном приросте или исправлении счётчиков источник остаётся неизвестным; причина записывается в результат сравнения. Сбой запроса не отменяет запись участника.

Это определение по разнице счётчиков, а не персональное поле Telegram. [stats.loadAsyncGraph](https://core.telegram.org/api/stats#chart-zooming) загружает график, если он возвращён асинхронно; увеличение доступно только при наличии `zoom_token`. Запросы списков вступивших по приглашениям и журнала администраторов пока не подключены.

Команда `/link campaign_name` помогает различать переходы по отдельным пригласительным ссылкам, но не добавляет признак Telegram Ads к вступлениям из нативной рекламы. Подтверждённый владельцем приход из Ads можно отметить вручную как `source: { "type": "ads", "name": null, "attribution": "manual", "confirmedBy": "owner" }`. Для подтверждённого перехода по ссылке используется тот же формат с `"type": "url"`; он не утверждает, что Telegram передал `invite_link`. Это ручные пометки, исходные события debug-журнала при этом не меняются.

### Локальная авторизация аккаунта Telegram

1. Получите собственные `api_id` и `api_hash` в [API development tools](https://my.telegram.org/apps), следуя [инструкции Telegram](https://core.telegram.org/api/obtaining_api_id).
2. Добавьте их в локальный `.env` как `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`. `OWNER_ID` должен соответствовать аккаунту, которым вы войдёте.
3. Установите зависимости через `npm install` (включая devDependencies) и запустите `npm run telegram:login` в своём терминале.
4. На телефоне откройте Telegram → Настройки → Устройства → Подключить устройство, отсканируйте актуальный QR-код и подтвердите вход. Если запрошен пароль двухэтапной защиты, введите его в терминале: ввод скрыт, пароль не сохраняется.
5. Проверьте повторный доступ командой `npm run telegram:check`. Проверка использует сохранённую сессию и сверяет аккаунт с `OWNER_ID`, без нового входа.

Сессия находится в `.telegram/user.session`: каталог имеет права `700`, файл — `600`, весь каталог исключён из Git и отделён от бэкапов `data/`. Сессия даёт доступ к пользовательскому аккаунту; не публикуйте её и не передавайте вместе со статистикой. Отозвать этот вход можно в Telegram → Настройки → Устройства, выбрав `Channel Stat Bot (local)`. Скрипт использует teleproto, сохраняет только сессию владельца, не запускает polling бота и не отправляет сообщения. Этот вход остаётся локальным; на Railway сессия автоматически не переносится.

Для Railway задайте `TELEGRAM_SESSION_PATH=/app/data/.telegram/user.session`, выполните отдельный вход на сервере и включите `SOURCE_STATS_ENABLED=1`. Сессия и JSON-файлы сохраняются на volume `/app/data` между деплоями. `api_id` и `api_hash` сами по себе не заменяют авторизованную сессию. Не копируйте серверную сессию для параллельного локального подключения и не включайте `/app/data/.telegram/` в выгрузки статистики. `.railwayignore` исключает локальные секреты, сессию и данные из исходников деплоя.

### Ежедневная сводка

При `SOURCE_STATS_ENABLED=1` ежедневная сводка включена автоматически; `DAILY_SUMMARY_ENABLED=0` отключает её. Используется уже авторизованная сессия владельца. Бот присылает сводку владельцу каждый день в **06:00 Europe/Podgorica**, с учётом переходов на летнее и зимнее время. Сам бот должен постоянно работать; отдельное задание cron не требуется.

Формат сообщения: заголовки и подпись «Пост:» выделены жирным. Подписи количества подписавшихся, отписавшихся, общего числа подписчиков, просмотров, реакций и репостов — обычным шрифтом, а их числовые значения вместе с приростом в скобках — жирным.

```text
📈 Статистика за 28.09.2026

Пользователей добавилось на канал: 7
Пользователей отписалось: 2
Общее число подписчиков: 1234

Информация по пяти последним постам

Пост: первые 100 символов текста или подписи https://t.me/c/1234567890/30
Количество просмотров: 350 (+50)
Количество реакций: 9 (-2)
Количество репостов: 5 (0)
```

Блок поста повторяется для пяти последних публикаций на конец отчётного дня, начиная с самой новой. Сегодняшние публикации не входят в отчёт за вчера. Если публикаций меньше пяти, выводятся все доступные. Для поста без текста используется «Пост без текста». Ссылки ведут на сообщения настроенного канала; предпросмотр ссылок отключён. Строк с временем получения счётчиков и диапазоном времени нет.

Вступления и выходы считаются по событиям в `channel-members.json` за те же сутки UTC, что и графики постов: от полуночи отчётного дня включительно до следующей полуночи, не включая правую границу. Например, отчёт 29 сентября в 06:00 по Подгорице содержит события за 28 сентября с 00:00 до 23:59:59 UTC. Повторное вступление и последующий выход учитываются как новые события. Переходы на летнее и зимнее время меняют момент отправки относительно UTC, но не границы статистики. События, которых бот не получил, этим подсчётом не восстанавливаются. Общее число подписчиков бот получает напрямую из Telegram при подготовке сводки или вызове `/stats`; это текущий показатель на момент запроса, а не число на конец отчётного дня.

Публикации выбираются независимо от входящих событий через [messages.getHistory](https://core.telegram.org/method/messages.getHistory). Исторические просмотры и репосты получаются через [stats.getMessageStats](https://core.telegram.org/method/stats.getMessageStats) в `stats_dc` канала: суммируются интервалы `Views` и `Shares` из `views_graph` с момента публикации до начала и до конца отчётного дня. Асинхронные графики загружаются через `stats.loadAsyncGraph`. Для стабильных названий графиков пользовательский клиент запрашивает английский язык. Альбом считается одной публикацией: используются счётчики первого сообщения и первая непустая подпись, без суммирования просмотров отдельных фотографий. Эти запросы не увеличивают просмотры и не отмечают сообщения прочитанными.

Основное число — накопленный результат на конец отчётного дня, а в скобках — прирост за эти сутки UTC: разница между результатом на конец и на начало дня. Например, `101 (+25)` означает 101 просмотр к концу 28 сентября, из которых 25 получены за 28 сентября. Если новых реакций или репостов не было, прежние значения сохраняются: `19 (0)` и `1 (0)`. Для поста, опубликованного в отчётный день, начальный счётчик равен нулю. История просмотров и репостов доступна даже до первой автоматической сводки: накапливать локальные дневные снимки для них не требуется. В итог входит вся история с момента публикации, без интервалов после конца отчётного дня и без пересчёта на Подгорицу. Если Telegram не предоставляет полную историю для расчёта просмотров или репостов, отображается «нет данных». Графики могут обновляться с задержкой со стороны Telegram.

Реакции считаются по сумме `message.reactions.results[].count`, включая обычные и кастомные эмодзи. График `reactions_by_emotion_graph` не используется: его сумма может не совпадать с количеством реакций под сообщением. В полночь UTC бот независимо запрашивает пять последних постов и сохраняет их счётчики в `reactionSnapshots` файла `data/daily-summary.json`. Снимки собираются и при отключённой автоматической отправке, если включён `SOURCE_STATS_ENABLED=1`, чтобы команда `/stats` тоже получала суточный прирост. Сохранённые снимки не заменяются повторными запросами и переживают перезапуск.

Запрос снимка запускается в полночь; допускается задержка получения до двух минут, а фактическое время сохраняется в `capturedAt`. Если бот не работал в это окно или Telegram не ответил вовремя, снимок за пропущенную границу не создаётся задним числом. Без снимка на конец дня показывается реальное текущее количество, например `19 (сейчас; нет данных за сутки)`, без прироста. Если конец дня известен, но нет начального снимка для старого поста, показывается `19 (нет данных за вчера)`. После двух соседних снимков появляется суточная разница, в том числе отрицательная при удалении реакций. У нового поста достаточно снимка на конец дня: на начало дня его ещё не было. Точную историю реакций до включения этой функции восстановить по текущим счётчикам нельзя.

Готовые сообщения, накопленные счётчики на начало и конец суток и подтверждения отправки сохраняются в `data/daily-summary.json` на том же volume `/app/data`. При первом включении бот ждёт ближайших 06:00, не отправляя сводку за уже прошедшее время. После перезапуска подтверждённые сводки не повторяются, а неотправленное готовое сообщение повторяется без нового запроса счётчиков. При ошибке Telegram запрос или отправка повторяются через минуту либо после указанного API срока ожидания. Если пропущено несколько дней, бот готовит только последнюю сводку, срок отправки которой уже наступил. Если Telegram принял сообщение, но процесс завершился до сохранения подтверждения, повторная доставка после перезапуска возможна. Формат хранилища — версия 4: отчёты версии 1 за период 11:00–11:00 сохраняются в `legacyReports`, версии 2 со сравнением активности двух дней — в `legacyActivityReports`, версии 3 с реакциями из графика — в `legacyReactionReports`. Старые значения не используются в новых расчётах. Уже отправленный календарный отчёт не дублируется при обновлении; `/stats` получает исправленный расчёт заново.

`/stats` читает сохранённую календарную сводку за вчера, если она уже подготовлена и содержит реакции на конец дня. В остальных случаях команда получает данные заново, в том числе до 06:00; это позволяет обновлять текущее количество реакций, пока исторические снимки недоступны. Команда не записывает снимки, не меняет время автоматической отправки и не помечает ежедневную сводку отправленной. Повторный `/stats` всегда отвечает заново.

### URL-кампании

В личном чате владельца команда `/promo` последовательно спрашивает название, дату начала в формате `ДД.ММ.ГГГГ` и длительность в календарных днях. `/cancel` отменяет ввод. Даты считаются по времени Подгорицы: день начала включён, последний день тоже включён. Пересекающиеся периоды отклоняются, потому что по одному источнику URL нельзя надёжно различить две одновременные кампании.

Кампании сохраняются в `data/url-promos.json` на том же постоянном томе `/app/data`. После сохранения бот размечает уже записанные вступления с источником URL за этот период в поле `urlCampaign`. Новым вступлениям с URL кампания назначается до отправки уведомления, в котором появится `Источник: URL (название кампании)`. Если источник определяется позднее по статистике, привязка происходит после его определения. Уже отправленные уведомления задним числом не повторяются. В других источниках и существующих кампаниях бот ничего не меняет. Назначение основано на дате и источнике, а не на индивидуальной ссылке пользователя.

### Объявления Telegram Ads

Чтобы дополнительно определять объявление для вступлений с источником Ads, задайте `TELEGRAM_ADS_API_TOKEN` из вкладки API рекламного кабинета в `.env` и в Railway Variables. Требуется `SOURCE_STATS_ENABLED=1`. Непустой токен включает проверку объявлений при следующем запуске. В `.env.example` значение пустое. Проверка доступа без запуска бота и без изменения данных: `npm run ads:check`.

Используется официальный [Telegram Ads API](https://ads.telegram.org/docs/api): `https://promoteapi.telegram.org/getCurrentAccount` и `getAdsList`, авторизация через заголовок `Authorization: Bearer`. Бот читает все страницы списка, включая остановленные объявления, и выбирает объявления с `action_type=join`, ведущие в настроенный канал. Счётчик `actions` у таких объявлений означает вступления. Просмотры, клики и конверсии других типов не участвуют в сравнении. Канал должен иметь публичный username; объявления по нераспознаваемым ссылкам не учитываются. Вызовы создания, редактирования рекламы и изменения бюджетов отсутствуют.

При запуске сохраняется исходный снимок. После нового вступления бот сначала определяет общий источник, затем сравнивает счётчики объявлений. Если прирост относится ровно к одному объявлению и равен числу ожидающих участников с источником Ads, им назначается это объявление. Новые объявления сравниваются с нулевым счётчиком, поэтому единственный прирост в новой кампании тоже может определить её. Удаление объявления с нулём вступлений не мешает сравнению остальных кампаний. Пока источник или рекламные счётчики не обновились, проверка повторяется каждые 30 секунд. Уведомление о вступлении отправляется сразу; через 30 минут без результата бот предлагает указать источник вручную. При нескольких выросших объявлениях, лишних вступлениях, уменьшении счётчиков, удалении объявления с ненулевым счётчиком или изменении ссылки результат остаётся неопределённым. Вступления до первого снимка не получают кампанию задним числом.

Это сопоставление агрегированных счётчиков, а не переданный Telegram идентификатор рекламы конкретного человека: задержки и пересчёты статистики могут приводить к ошибкам предположения. Назначение помечено `attribution: statistics_delta`. Существующие ручные источники не меняются, прежние участники автоматически не размечаются.

Рекламные счётчики хранятся отдельно в `data/ads-statistics.json`: `baseline` — использованный снимок, `days` — последние снимки по дням UTC, `decisions` — решения с исходными значениями и приростом. Сами счётчики накопительные за всё время объявления и не обнуляются в полночь. В `channel-members.json` поле `adsCampaign` хранит статус проверки и, при успешном сопоставлении, аккаунт, ID и название объявления. Атомарная запись и журнал решений позволяют продолжить обработку после перезапуска между записями двух файлов. Токен в этих файлах не сохраняется. Файл статистики также находится на volume `/app/data` и исключён из Git вместе с остальными данными и бэкапами.
