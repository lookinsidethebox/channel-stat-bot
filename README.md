# Channel Stat Bot

Telegram-бот на Node.js и Telegraf для учёта вступлений и выходов из одного канала. Сохраняет периоды подписки, источник вступления и превью поста, полученного отдельным запросом к Telegram на момент события; отправляет владельцу уведомления.

## Запуск

1. Установите зависимости: `npm install`.
2. Скопируйте `.env.example` в `.env` и заполните настройки:
   - `BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather).
   - `OWNER_ID` — положительный числовой ID вашего Telegram-аккаунта.
   - `CHANNEL_ID` — отрицательный числовой ID канала, обычно начинающийся с `-100`. Имя вида `@channel` не подходит для сравнения с входящими событиями.
3. Добавьте бота администратором канала, чтобы Telegram присылал события об изменении участников.
4. Чтобы создавать размеченные ссылки, выдайте боту право приглашать пользователей (`can_invite_users`).
5. Откройте личный чат с ботом и отправьте `/start`, чтобы он мог присылать вам уведомления. Команда `/link campaign_name` создаёт ссылку для рекламного источника; метка должна содержать от 1 до 32 символов.
6. Для разработки запустите `npm run dev` (nodemon следит только за JavaScript в `src/`, поэтому запись статистики не перезапускает бота).
7. Для обычного запуска используйте `npm start`.

Отслеживаемый канал должен быть указан как личный канал в профиле владельца (`OWNER_ID`). Бот проверяет, что его ID совпадает с `CHANNEL_ID`, и получает существующие посты через [getUserPersonalChatMessages](https://core.telegram.org/bots/api#getuserpersonalchatmessages). Для этого не нужно публиковать тестовый пост или входить в Telegram от имени пользователя.

Файл `.env` исключён из Git. Команды и текстовые сообщения доступны только владельцу. Ответ на обычный текст и `/start` пока остаётся `Hello, world!`.

## Проверка

Запустите `npm test`. Тесты работают с временными файлами и подменёнными вызовами Telegram, без токена и подключения к сети.

Для живой проверки добавьте `DEBUG_MEMBER_UPDATES=1` в `.env` и перезапустите бота. В `data/debug-member-updates.jsonl` появятся исходные события `chat_member` настроенного канала и результат их обработки. После проверки выключите флаг: журнал содержит данные участников и растёт при новых событиях.

На Railway этот флаг нужно задавать в Variables сервиса: локальный `.env` не переносится на сервер. При `DEBUG_MEMBER_UPDATES=0` или отсутствующем значении обработчик журнала не подключается и файл не создаётся. При включённом журнале запись `observer_started` создаётся сразу при запуске, ещё до первого вступления. Для сохранения статистики и журнала между деплоями подключите постоянный volume к `/app/data`.

## Структура

- `src/index.js` — загрузка `.env`, запуск и остановка бота.
- `src/config.js` — чтение и проверка настроек.
- `src/bot.js` — сборка бота и регистрация обработчиков без запуска polling.
- `src/controllers/` — команды, события участников и посты канала.
- `src/middleware/owner-only.middleware.js` — доступ владельца к командам и сообщениям.
- `src/middleware/ordered-channel-updates.middleware.js` — обработка событий канала в порядке получения, включая события из одной пачки Telegram.
- `src/services/member-event.service.js` — преобразование событий Telegram и создание превью постов.
- `src/services/channel-post.service.js` — запрос последних постов и выбор публикации на момент вступления или выхода.
- `src/storage/member.store.js` — хранение статистики в JSON и последовательная очередь записи.
- `tests/` — проверки обработчиков, хранения и их совместной работы.

## Данные

Файл `data/channel-members.json` создаётся автоматически и не попадает в Git. Формат: `{ latestPost, members }`. Каждая запись `members` описывает один период подписки; выход без известного вступления сохраняется с `addedAt: null`. Повторное вступление после выхода помечается `returned: true`.

Вступление при уже открытом периоде подписки и повторный выход с тем же временем не создают новых записей или уведомлений. События старше последнего сохранённого изменения участника игнорируются. Уже накопленные записи автоматически не очищаются.

Запись выполняется через временный файл с последующим переименованием. Повреждённый JSON или неподходящая структура вызывают ошибку, исходный файл сохраняется. Запускайте один экземпляр бота на файл данных: очередь защищает записи внутри одного процесса.

При каждом вступлении и выходе бот отдельно запрашивает до 20 последних постов и выбирает последнюю публикацию, опубликованную не позже события. В `postAtAddition` или `postAtRemoval` попадают первые 100 Unicode-символов её текста или подписи. Для этого не требуется ранее получать событие `channel_post`. Поле `postedAt` в снимке хранит время публикации или последней учтённой правки. Для постов без текста превью равно `null`.

Если запрос не удался, канал не привязан к профилю, событие старше доступных 20 публикаций или нужный пост отредактирован уже после события, членство всё равно сохраняется. Причина отсутствия снимка записывается в `postAtAdditionError` или `postAtRemovalError` и включается в уведомление владельцу. Пустой канал даёт `null` без ошибки. Удалённые посты и прежние версии отредактированного текста этот запрос восстановить не может.

`latestPost` остаётся локальным снимком для просмотра, но не используется вместо запроса при записи членства. Новые посты и правки также обновляют этот снимок; существующие снимки в записях участников остаются прежними.

### Способ вступления и статистика источников

В [ChatMemberUpdated](https://core.telegram.org/bots/api#chatmemberupdated) доступны `invite_link`, `via_chat_folder_invite_link` и `via_join_request`. Обработчик сохраняет их как `invite_link`, `chat_folder` и `join_request` соответственно. Если этих признаков нет, сохраняется `unknown`: это не означает органический переход или отсутствие рекламы.

Категории из статистики канала нельзя целиком восстановить для каждого подписчика по событиям Bot API:

| Категория статистики | Что доступно при вступлении |
| --- | --- |
| URL | `invite_link` позволяет определить вступление по пригласительной ссылке, когда Telegram передал её. Это не универсальный признак перехода по любому URL и не гарантированное соответствие категории статистики. |
| Ads | Отдельного признака в `ChatMemberUpdated` нет. |
| Shareable Chat Folders | `via_chat_folder_invite_link: true`. |
| Search | Отдельного признака в `ChatMemberUpdated` нет. |
| PM | Отдельного признака в `ChatMemberUpdated` нет. Поле `from` обозначает исполнителя изменения, а не чат, из которого пришёл пользователь. |

Общие числа по источникам доступны в `stats.broadcastStats.new_followers_by_source_graph` через [stats.getBroadcastStats](https://core.telegram.org/method/stats.getBroadcastStats). Этот метод Telegram API доступен пользовательским аккаунтам, а не ботам. Он возвращает график статистики, а не соответствие источников конкретным подписчикам.

Дополнительные запросы пользовательского Telegram API могут восстановить часть сведений о вступлениях. [messages.getChatInviteImporters](https://core.telegram.org/method/messages.getChatInviteImporters) возвращает участников конкретной пригласительной ссылки с `user_id` и временем вступления; [channels.getAdminLog](https://core.telegram.org/method/channels.getAdminLog) позволяет проверить доступные события, включая вступление по приглашению. Эти методы требуют пользовательского аккаунта с правами администратора и недоступны с токеном бота. Они не дают универсальную привязку Ads / Search / PM к пользователю и не распространяются на любую публичную ссылку вида `t.me/channel`.

При `SOURCE_STATS_ENABLED=1` бот после каждого нового вступления запрашивает этот график и сравнивает накопительные счётчики за день UTC с предыдущим снимком. Например, `Ads=1, URL=0` → `Ads=1, URL=1` означает URL для следующего участника; последующий рост до `Ads=2, URL=1` означает Ads. Для первого дня работы бот сначала получает исходный снимок; в новом дне сравнение начинается с нулей. Выходы и повторно доставленные события не запускают запрос.

Счётчики хранятся отдельно в `data/source-statistics.json`: `days` содержит предыдущие использованные `counts`, последние полученные `observedCounts` и время проверки; `pending` — ожидающие вступления, `decisions` — результаты сравнения с разницей счётчиков. В `channel-members.json` остаются участники, их `source` и статус проверки `sourceLookup`, без дневных счётчиков. Решение сначала сохраняется в файле статистики, затем применяется к участнику; после прерывания между записями оно применяется повторно без повторного расходования прироста.

Если вырос ровно один источник на число ожидающих вступлений, участники получают этот источник с `attribution: "statistics_delta"`. Подтверждённые владельцем источники и сведения Bot API сохраняют приоритет. Если Telegram ещё не обновил график, исходные счётчики не расходуются: бот повторяет проверку через 30 секунд и присылает уточнение после определения источника. Ограничение Telegram `FLOOD_WAIT` увеличивает паузу. При неоднозначном приросте или исправлении счётчиков источник остаётся неизвестным; причина записывается в результат сравнения. Сбой запроса не отменяет запись участника.

Это определение по разнице счётчиков, а не персональное поле Telegram. [stats.loadAsyncGraph](https://core.telegram.org/api/stats#chart-zooming) загружает график, если он возвращён асинхронно; увеличение доступно только при наличии `zoom_token`. Запросы списков вступивших по приглашениям и журнала администраторов пока не подключены.

Команда `/link campaign_name` помогает различать переходы по отдельным пригласительным ссылкам, но не добавляет признак Telegram Ads к вступлениям из нативной рекламы. Подтверждённый владельцем приход из Ads можно отметить вручную как `source: { "type": "ads", "name": null, "attribution": "manual", "confirmedBy": "owner" }`. Для подтверждённого перехода по ссылке используется тот же формат с `"type": "url"`; он не утверждает, что Telegram передал `invite_link`. Это ручные пометки, исходные события debug-журнала при этом не меняются.

### Локальная авторизация аккаунта Telegram

1. Получите собственные `api_id` и `api_hash` в [API development tools](https://my.telegram.org/apps), следуя [инструкции Telegram](https://core.telegram.org/api/obtaining_api_id).
2. Добавьте их в локальный `.env` как `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`. `OWNER_ID` должен соответствовать аккаунту, которым вы войдёте.
3. Установите зависимости через `npm install` (включая devDependencies) и запустите `npm run telegram:login` в своём терминале.
4. На телефоне откройте Telegram → Настройки → Устройства → Подключить устройство, отсканируйте актуальный QR-код и подтвердите вход. Если запрошен пароль двухэтапной защиты, введите его в терминале: ввод скрыт, пароль не сохраняется.
5. Проверьте повторный доступ командой `npm run telegram:check`. Проверка использует сохранённую сессию и сверяет аккаунт с `OWNER_ID`, без нового входа.

Сессия находится в `.telegram/user.session`: каталог имеет права `700`, файл — `600`, весь каталог исключён из Git и отделён от бэкапов `data/`. Сессия даёт доступ к пользовательскому аккаунту; не публикуйте её и не передавайте вместе со статистикой. Отозвать этот вход можно в Telegram → Настройки → Устройства, выбрав `Channel Stat Bot (local)`. Скрипт использует teleproto, сохраняет только сессию владельца, не запускает polling бота и не отправляет сообщения. Этот вход остаётся локальным; на Railway сессия автоматически не переносится.

Для Railway задайте `TELEGRAM_SESSION_PATH=/app/data/.telegram/user.session`, выполните отдельный вход на сервере и включите `SOURCE_STATS_ENABLED=1`. Сессия и JSON-файлы сохраняются на volume `/app/data` между деплоями. `api_id` и `api_hash` сами по себе не заменяют авторизованную сессию. Не копируйте серверную сессию для параллельного локального подключения и не включайте `/app/data/.telegram/` в выгрузки статистики. `.railwayignore` исключает локальные секреты, сессию и данные из исходников деплоя.

### Объявления Telegram Ads

Чтобы дополнительно определять объявление для вступлений с источником Ads, задайте `TELEGRAM_ADS_API_TOKEN` из вкладки API рекламного кабинета в `.env` и в Railway Variables. Требуется `SOURCE_STATS_ENABLED=1`. Непустой токен включает проверку объявлений при следующем запуске. В `.env.example` значение пустое. Проверка доступа без запуска бота и без изменения данных: `npm run ads:check`.

Используется официальный [Telegram Ads API](https://ads.telegram.org/docs/api): `https://promoteapi.telegram.org/getCurrentAccount` и `getAdsList`, авторизация через заголовок `Authorization: Bearer`. Бот читает все страницы списка, включая остановленные объявления, и выбирает объявления с `action_type=join`, ведущие в настроенный канал. Счётчик `actions` у таких объявлений означает вступления. Просмотры, клики и конверсии других типов не участвуют в сравнении. Канал должен иметь публичный username; объявления по нераспознаваемым ссылкам не учитываются. Вызовы создания, редактирования рекламы и изменения бюджетов отсутствуют.

При запуске сохраняется исходный снимок. После нового вступления бот сначала определяет общий источник, затем сравнивает счётчики объявлений. Если прирост относится ровно к одному объявлению и равен числу ожидающих участников с источником Ads, им назначается это объявление. Пока источник или рекламные счётчики не обновились, проверка повторяется каждые 30 секунд. Когда уточнение приходит позже, владелец получает отдельное уведомление. При нескольких выросших объявлениях, лишних вступлениях, уменьшении счётчиков или изменении набора объявлений результат остаётся неопределённым. Вступления до первого снимка не получают кампанию задним числом.

Это сопоставление агрегированных счётчиков, а не переданный Telegram идентификатор рекламы конкретного человека: задержки и пересчёты статистики могут приводить к ошибкам предположения. Назначение помечено `attribution: statistics_delta`. Существующие ручные источники не меняются, прежние участники автоматически не размечаются.

Рекламные счётчики хранятся отдельно в `data/ads-statistics.json`: `baseline` — использованный снимок, `days` — последние снимки по дням UTC, `decisions` — решения с исходными значениями и приростом. Сами счётчики накопительные за всё время объявления и не обнуляются в полночь. В `channel-members.json` добавляются только `campaign` (аккаунт, ID и название объявления, способ сопоставления) и `campaignLookup` (статус проверки). Атомарная запись и журнал решений позволяют продолжить обработку после перезапуска между записями двух файлов. Токен в этих файлах не сохраняется. Файл статистики также находится на volume `/app/data` и исключён из Git вместе с остальными данными и бэкапами.
